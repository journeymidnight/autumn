Current summary:
  Branch: perf-r1-partition-scale-out (worktree /data/dongmao_dev/autumn-perf-r1)

  Extended `autumn-client perf-check` with a per-thread pipeline depth
  knob so the benchmark can fire up to K concurrent in-flight Put/Get
  requests per worker thread instead of the previous sync loop
  (one-in-flight-per-thread). This is the client-side counterpart to
  R4 steps 4.1-4.4 (SQ/CQ everywhere): now the benchmark can actually
  stress-test the pipelined server.

  Changes:
    crates/server/src/bin/autumn_client.rs
      • PerfCheck variant gains `pipeline_depth: usize` field.
      • CLI parser adds `--pipeline-depth K`, validated [1, 256], default 1.
      • usage() help text updated.
      • Write-phase worker rewritten: FuturesUnordered sliding window
        of up to `max_depth` in-flight ps.call(MSG_PUT, …) futures.
        Refill while inflight.len() < max_depth && SystemTime::now()
        < deadline; drain one completion per outer iteration; when
        deadline passes and inflight is empty, next().await → None →
        break.
      • Read-phase worker rewritten with the same pattern, using
        MSG_GET. Per-thread RpcClient conn cache preserved.
      • Summary header prints `depth=K` only when K > 1
        (== diff-stable vs baseline output for K=1).

    crates/server/Cargo.toml
      • Adds `futures = "0.3"` (needed for FuturesUnordered / StreamExt).

    perf_check.sh
      • Parses `--pipeline-depth K` (validates [1, 256]), forwards to
        `autumn-client perf-check --pipeline-depth K`. Default 1.

  Key correctness points (verified by behaviour):
    - At `--pipeline-depth 1`, observable output (ops/s) matches the
      pre-change baseline (~57k write / 76k read on 3-rep shm, N=1).
    - Deadline semantics preserved: refill stops once deadline hits,
      but already-submitted in-flight requests drain (same as before).
    - Error handling: only ok results count toward total_ops; errors
      are silently dropped exactly like before.
    - `RpcClient::connect` returns `Rc<Self>`, which is cheap to clone
      into each inflight future — no Arc/spawn overhead per request.

Verification / smoke runs (3-rep shm cluster, N=1 partition,
4 KB values, nosync, 10s, 256 threads):

  --pipeline-depth 1   → write=57 316 ops/s  read=76 053 ops/s
  --pipeline-depth 4   → write=55 168 ops/s  read=88 212 ops/s
  --pipeline-depth 8   → write=50 639 ops/s  read=68 870 ops/s
                         (first run at d=8 tipped over on connection
                          back-pressure — pre-existing RpcClient
                          submit-channel hang when writer_task exits
                          on broken-pipe; second run clean. Out of
                          scope for Task A, not changing library
                          crates per spec.)

  Interpretation: reads scale with depth at N=1 (+16% at d=4), but
  writes don't — the 256-thread × 4 KB × nosync path is still bound
  on the group-commit ceiling the PS-side ps_bench also revealed
  (Task B output). The benchmark's CLIENT is no longer the
  bottleneck — that's the change's deliverable.
