Current summary (F099-A):
  Branch: perf-r1-partition-scale-out (worktree /data/dongmao_dev/autumn-perf-r1)

  Captured 3 flame graphs of autumn-ps under the three scenarios listed
  in the F099-A spec. Root cause identified: the 60-65 k write ceiling
  at N=1 x 256 synchronous x 4 KB is a CPU ceiling on the single
  `part-13` (P-log) OS thread, not an I/O ceiling.

  Breakdown of P-log CPU at the ceiling (scenario a, 256 x d=1 write):
    - 28 %  crossbeam-skiplist atomic ops during Memtable::insert
            (SkipList::search_position + refcount cascades)
    - 30 %  per-request RPC ceremony (spawn_write_request task +
            handle_put's inner oneshot + waker cascade drops)
    - 16 %  background_write_loop_r1 Phase 1 + Phase 3
    -  4 %  StreamClient::append* (I/O is NOT the bottleneck)
    -  4 %  flush dispatcher
    -  18 %  compio scheduler, io_uring CQE drain, misc allocs

  fsync and 3-replica fanout are both ruled out as the bottleneck.
  Reads escape the ceiling because handle_get runs inline on ps-conn
  threads (parallel), doesn't touch the skiplist except for search,
  and has only one oneshot per request.

  Candidate fixes for F099-B+ (priority order):
    1. Replace SkipMap with single-writer BTreeMap for the active
       memtable. Est. +25-40 %.
    2. Collapse spawn_write_request task + handle_put inner oneshot
       into direct enqueue. Est. +10-15 %.
    3. Coalesce Bytes cloning during WAL encode. Est. +3-6 %.

  Fixes A+B combined are expected to move median write throughput
  from ~55 k to ~70-75 k, clearing the Tier B' 65 k gate.

Current summary:
  Branch: perf-r1-partition-scale-out (worktree /data/dongmao_dev/autumn-perf-r1)

  Changed the sequential per-replica send_vectored loop inside
  crates/stream/src/client.rs::launch_append (lines 525–550) to fire
  all 3 replicas concurrently via futures::future::join_all. Under
  high submission rate each RpcClient's submit channel can briefly
  block (microseconds but measurable); firing the 3 futures in
  parallel lets each replica's submit_tx.send(...).await progress
  independently instead of serialising on replica 0 -> 1 -> 2.

  Correctness preservation (verified by review + tests):
    - Per-replica TCP byte order is unchanged (each RpcClient runs
      one single-writer writer_task post-R4 4.1; fanout only
      parallelises the 3 SUBMITS, not the per-conn writes).
    - Lease order -> TCP order -> commit-truncation order invariant
      holds because lease is serialised by the worker actor; each
      replica's socket still receives frames in lease order.
    - apply_completion's first-err-wins + offset-consistency checks
      preserved: we use join_all (NOT try_join_all) so all 3 slots
      are filled as Result<Receiver<Frame>> regardless of which
      one errors; apply_completion iterates and short-circuits
      on the first error exactly as before.
    - hdr and payload_parts are Bytes -> Arc-backed; per-replica
      clones are cheap Arc refcount bumps (no deep copy). The outer
      Vec allocation (~24 bytes x 3) is negligible.
    - ConnPool::get_client is safe under concurrent calls: RefCell
      borrow never spans an await, and the 3 replicas have distinct
      SocketAddrs so no cache collision. (Worker is single-task so
      no thread-safety concern either.)

  Changes:
