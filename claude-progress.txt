  Branch: perf-r1-partition-scale-out (worktree /data/dongmao_dev/autumn-perf-r1)

  Replaced the step-4.3 double-buffer write loop (at most ONE Phase 2
  future in flight) with a FuturesUnordered-driven N-deep pipeline on
  both the P-log and P-bulk threads.  This is the client of step 4.3's
  per-stream SQ/CQ worker — before this change, P-log was serializing
  at 1 outstanding `append_batch` per partition, leaving the step-4.3
  capacity unused in the hot path.

  Architecture:
    crates/partition-server/src/background.rs
      • background_write_loop_r1 rewritten:
          FU<Pin<Box<dyn Future<Output=InflightCompletion>>>> cap=8
          (env AUTUMN_PS_INFLIGHT_CAP, clamped [1, 64]).
          Per-iteration: drain ready completions via now_or_never →
          run Phase 3, then branch on (n_inflight, at_cap):
            ready_to_launch (pending + cap room + gate) → launch
            at_cap                                        → await CQ only
            n_inflight==0 & nothing to launch            → await SQ alone
            otherwise                                    → select(SQ, CQ)
          Shutdown (write_rx closed): drain all inflight, flush residual
          pending as one last batch, emit metrics.
      • MIN_PIPELINE_BATCH = 256 gate (R3 Task 5b insight) — a SECOND or
        later batch requires pending >= 256 before launch; the first
        batch (n_inflight == 0) always launches.  Avoids the "small
        fragmented batches steal from naturally-large bursts" regression.
      • Phase 1 / Phase 3 primitives (start_write_batch / finish_write_batch
        / InFlightBatch) preserved exactly — the refactor is purely about
        the loop that schedules them.
      • Out-of-order Phase-2 completion is handled correctly:
          seq numbers assigned in Phase 1 in launch order
          memtable MVCC keys are self-sorting (internal key = user_key ++
            0x00 ++ BE(u64::MAX - seq)) so insertion order doesn't matter
          client oneshot replies are per-request
          logStream offsets preserved by the step-4.3 stream worker's
            lease/ack cursor

    crates/partition-server/src/lib.rs
      • flush_worker_loop rewritten on same pattern, cap=2 (env
        AUTUMN_PS_BULK_INFLIGHT_CAP, clamped [1, 16]).  Each in-flight
        flush holds a 128 MB SST buffer in RAM — cap deliberately small.
        Overlaps `build_sst_bytes` (CPU, spawn_blocking) of the next
        flush with the current flush's 128 MB `row_stream.append`
        (network).
      • ps_inflight_cap() and ps_bulk_inflight_cap() env getters added
        using OnceLock, ranges clamped as above.

    Tier verdict: baseline preserved, below 70k / Tier B' gate.  The
    single-partition × 256-sync-client workload is fundamentally
    constrained by 256 × RTT (~4ms) = 64k ceiling; both R3 and the R4
    4.4 spec explicitly flagged this (see spec §4 Tier B' rationale +
    Task 5b regression).  The refactor IS architecturally correct and
    unlocks concurrent Phase-2 issuance at the PS layer — but with
    synchronous clients that wait for each reply before submitting,
    pending doesn't grow WHILE inflight is active, so effective
    pipeline depth stays near 1 during steady-state burst cycling.
    Average batch size observed in metrics: 128 ops (vs 256 cap), with
    2ms avg Phase 2 — consistent with effective depth ~1.5-2 but still
    RTT-bound overall.

Main gaps / concerns:
  1. Write throughput median 52.7k is within run-to-run noise of the
     post-4.3 baseline (51-56k across prior runs).  Not a regression,
     but also not the 70-80k the spec aspired to.  The spec itself
     says "Real gains depend on TCP write bandwidth to replicas and
     disk fsync latency; we're removing a pure-serialization
     bottleneck, not a real bottleneck, so expect ~50% improvement at
     realistic workload." — the shm/sync-256 workload isn't a realistic
     workload in that sense.  R4 Step 4.5 / 4.6 gate runs and any
     further pipelining at higher client counts / async workloads
     should now show the architectural benefit.
  2. MIN_PIPELINE_BATCH = 256 tuning: the gate's first-batch bypass
     (n_inflight == 0 always launches) means under sustained-burst
     cycling the pipeline oscillates between depth 1 and 2 — matches
     the observed 128 avg batch.  Lowering the gate would risk the 5b
     regression for non-barrier workloads; leaving at 256 preserves
     correctness for the primary benchmark shape.
