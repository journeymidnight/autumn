This session completed F099-N-b with a BIG finding:

ROOT CAUSE of the 60-65 k plateau at N=4 / N=8 × d=8 is NOT in the storage
stack at all. It is a workload-distribution bug in `autumn-client perf-check`:

  * Keys are `format!("pc_{tid}_{seq}")` — prefix byte 'p' = 0x70.
  * Partition ranges are hex-encoded; ASCII first bytes are 0x33 / 0x37 /
    0x62 (at N=4) or finer at N=8.
  * Every "pc_..." key falls into the LAST partition's range (part 34 at
    N=4, part 62 at N=8).
  * The client still stripes its 256 threads round-robin across all N
    partition ports, setting part_id == owner_part so each PS accepts the
    frame at the ps-conn decode layer. Then `start_write_batch.in_range()`
    rejects with "key is out of range" on N-1 of N partitions.
  * Reject P-log threads still burn 40-60 % CPU per core: decode → mpsc
    send → merged_partition_loop pickup → validate → send_err → encode
    error frame → io_uring write back to client.

Evidence (measured):
  * `autumn-client info` at end of N=4 × d=8 bench:
       part-34 log-stream = 63 GB, row-stream = 66 GB
       parts 13/20/27 log/row/meta = 0 B
  * PS log `partition write summary part_id=X`: ONLY part_id=34 emits
    records throughout the run (1.83 M ops on part-34, 0 on others).
  * Per-thread `top -H`: 4 P-logs at 99-100 % CPU — but only part-34-bulk
    runs (flush), other *-bulk threads are 0 %.
  * bpftrace per-thread: part-34 does 85k iouring_enter / 30s + 142
    eventfd writes + 67 futex (cross-thread coord). part-13 does 40k
    iouring_enter / 30s + ZERO writes + ZERO futex — pure reject loop.
  * Global tcp_sendmsg retbytes:
       part-13/20/27: ~4.7 MB/s each (tiny error frames at ~50 B)
       part-34:      648 MB/s (productive)
       part-34-bulk: 6.8 GB/s (SST upload)
  * PS kernel TCP CPU: 2.84 cores at N=4 vs 0.71 cores at N=1 for the
    SAME productive throughput — 4× waste on reject path round-trips.
  * Control: N=1 × d=8 gives 63.3 k write (single productive P-log).
    N=4 × d=8 gives 62.5 k median write. Same ceiling — exactly what
    "only one partition actually works" predicts.

All 7 hypotheses ruled out as independent causes:
  H1 client-side: 1-5 % per-thread CPU, no contention
  H2 PS-side: only part-34 P-log does real work; other 3 burn reject CPU
  H3 extent-node per-shard: 10-40 % CPU, plenty of headroom
  H4 kernel TCP: 2.84 cores at N=4 is symptom of H2, not cause
  H5 bootstrap extent distribution: all productive extents go to 1 stream
  H6 manager: 142 recv/s idle heartbeats only
  H7 combinatorial: only 9 PS→extent sockets total

Recommended F099-N-c (<1 day, zero risk, bench-tool only):
  * Fix key generation in crates/server/src/bin/autumn_client.rs for BOTH
    perf-check (line 1603) and wbench (line 1270) so each thread emits
    keys inside its assigned partition's range. Either expose the
    partition range from the manager and prefix each key with a hex byte
    in-range, or generate hex-prefixed keys derived from tid.
  * After fix, re-measure N ∈ {1, 2, 4, 8} × d=8. Expected write throughput
    rises from 62 k to 150-200 k at N=4 if each P-log keeps up. Any
    remaining gap IS the real next bottleneck — worth a follow-up
    diagnosis with the honest workload.
