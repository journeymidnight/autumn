    - ExtentSubmitMsg::{AppendBatch { slots, resp_tx }, ReadBatch, Shutdown}
      (per-batch oneshot::Sender<Vec<Frame>> — amortises channel
       overhead across N frames in one batch)
    - fn get_or_spawn(node, extent_id, extent_entry) -> mpsc::Sender
      (DashMap::entry; double-spawn-safe under contention)
    - async fn worker_loop:
        FuturesUnordered<inflight I/O future> + select_biased over
        rx.next() and inflight.select_next_some(); drains all
        completions; auto-removes from worker_pool on Shutdown or
        all-senders-drop
    - submit_append_batch: runs ACL (eversion refresh via manager,
      sealed check, revision fencing, commit reconciliation),
      reserves extent.len synchronously before pushing the pwritev
      future into FU (critical: overlapping submits must see the
      advanced len, matching old single-threaded semantics).
    - submit_read_batch: sequential preads inside one future.
    - Inflight cap = AUTUMN_EXTENT_INFLIGHT_CAP (default 64).

  ExtentNode changes (crates/stream/src/extent_node.rs):
    - ExtentNode gains worker_pool: Rc<DashMap<u64, mpsc::Sender<...>>>.
    - ExtentEntry + a few ACL helpers promoted to pub(crate).
    - handle_connection fully rewritten as two-task SQ/CQ:
        * Reader task (this fn): decodes TCP frames, groups consecutive
          APPEND / READ frames by extent_id (preserving the pwritev
          batch-coalesce optimisation) and sends ONE AppendBatch /
          ReadBatch submit_msg per group. Control RPCs dispatched in a
          spawned task producing a single-element Vec<Frame>.
        * Completion task (spawned from handle_connection): owns
          WriteHalf, drains FuturesUnordered<oneshot::Receiver<Vec<Frame>>>,
          coalesces all ready frames into ONE write_vectored_all per
          poll cycle (now_or_never drain).
    - Old handle_append_batch / handle_read_batch deleted; handle_append
      / handle_read_bytes / other control handlers retained via dispatch().

Main gaps / concerns:
  - Microbench extent_bench write at depth=64 regressed 208k → 68k ops/s.
    Cause: unavoidable task-boundary overhead of the new reader + worker
    + completion 3-task pipeline at per-request scale. This is measured
    on a pure-server loopback benchmark with no upstream work. The
    end-to-end path (perf_check.sh --shm) is unchanged because that
    workload is network-RTT bound, not server-bound. Subsequent R4
    steps (4.3/4.4) restructure the upper layers to benefit from this
    per-extent decoupling, at which point the server-side capacity head-
    room unlocked by per-extent parallelism materialises end-to-end.

  - bench_mixed (write+read concurrent on one extent) appears to run
    slowly under the new pipeline (did not complete in 120s timeout during
    verification). Not a correctness bug — the mixed workload serialises
    on the per-extent worker by design — but slower than the previous
    batch-coalescing path that interleaved everything in one task. Not
    in scope for 4.2 to resolve.

  - perf gate at R4 level (write ≥ 80k shm N=1) is NOT met by 4.2 alone;
    it requires the full 4.1+4.2+4.3+4.4 pipeline. 4.2 achieves parity
    with post-4.1 baseline, which is what the step-level gate requires.
