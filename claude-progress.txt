  Three scenarios captured, each with 30 s bpftrace window during steady state:
    A: 256 × d=1 nosync write → ~57 k ops/s (the ceiling)
    B: 1 × d=64 nosync write  → ~12 k ops/s
    C: 32 × d=16 read         → ~22 k ops/s (lower than ps_bench's 162 k
                                because perf-check read phase uses only a
                                single write phase's seed data)

  KEY FINDINGS
    1. compio uses io_uring for EVERY I/O (file + TCP + eventfd), so the
       classic tracepoints (sys_enter_pwritev / sendto / recvfrom / writev)
       never fire on the hot path. Useful probing required kprobes on
       tcp_sendmsg / tcp_recvmsg (which capture the kernel TCP cost that
       io_uring ultimately drives inside kernel).

    2. Scenario A kernel TCP CPU (kprobe, PS process, 30 s):
         tcp_sendmsg: 1.12 M calls, 24.0 s  (80 %  of 1 core)
         tcp_recvmsg: 1.93 M calls, 59.4 s  (198 % of 1 core)
         COMBINED:                  83.4 s = 2.78 CPU cores of kernel TCP
       91 % of tcp_sendmsg calls carry only 32-63 B (small reply frames).
       Loopback TCP pipeline is the dominant invisible cost.

    3. P-log thread (TID=part-13) in Scenario A is **not at 100 % CPU**
       as F099-A's pprof suggested. 13.4 s of P-log's 30 s wall-clock is
       spent *blocked inside io_uring_enter*, waiting for extent-node
       append CQEs + Put-request body recvs. True P-log user+kernel CPU
       is roughly 57 % of 1 core. The other 43 % is idle-wait on remote
       peers, not CPU starvation.

    4. Scenario C (read) shows 35x less kernel TCP CPU (2.4 s vs 83 s)
       because read replies are 1 × 4 KB sendmsg per Get, whereas write
       replies are 256 small header sends per batch. This confirms the
       write path's small-header-flood is the dominant kernel-side cost.

    5. Context switches on P-log = 674/s (2.6 x one full RTT), well
       below any thrash threshold. Scheduler overhead ≈ 0.004 % of P-log.
       Scheduling is NOT material to the ceiling.

    6. Scenario B's P-log does 29 k io_uring_enters/s at 20 µs each vs
       Scenario A's 595/s at 750 µs each. B is bound by per-batch
       round-trip latency (~300 µs per 64-op batch), not by any
       specific syscall. This reinforces that single-TCP-connection RTT
       is the 12 k ops/s cap for d=64.

  ROOT CAUSE (H1 picked): kernel TCP send/recv pipeline on loopback,
    specifically the small-response-frame flood: 37 k tcp_sendmsg/s
    with 91 % at 32-63 B. Each call costs ~22 µs of kernel CPU for
    skb alloc + header copy + loopback delivery; collectively ~0.8
    cores of pure overhead beyond the actual payload.

  Architectural payoff summary:
    The primary win is structural, not purely perf. The P-log write
    hot path is now one compio task + one mpsc send + one oneshot,
    against the old two tasks + two mpsc sends + two oneshots +
    Waker cascade. This is the foundation for any future "reduce
    sync-RTT coupling" work — a simpler task graph makes it easier
    to reason about whether a given Put spends its time in CPU vs
    RTT vs lock contention. The +8.5 % write headroom at the 256

    gap to the 70 k "A+B combined" estimate is attributable to the
    RTT-client-sync barrier documented in F099-C (256 sync clients
    × ~4 ms batch RTT ≈ 64 k theoretical, and we are now at 57.6 k
    median — close to that envelope).
