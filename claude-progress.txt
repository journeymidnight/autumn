Current summary:
  Branch: perf-r1-partition-scale-out (worktree /data/dongmao_dev/autumn-perf-r1)

  Replaced the v2 burst-structured handle_connection (commit b1a92f7) with
  a TRUE SQ/CQ loop: submission and completion run concurrently in the
  same task via `futures::future::select`, and completions flush out as
  soon as they happen (no burst boundary gating).

  Rationale: v2 restored microbench perf after the 3-task worker design
  (commit 3261702) regressed 3×, but did so by using a burst loop
  (`reader.read → push futures → while inflight.next().await → flush`).
  In a mixed burst with 1 slow must_sync append + 100 fast reads, all
  100 read responses would sit in tx_bufs waiting for the append's
  pwritev+sync to finish. That is NOT SQ/CQ — SQ and CQ were strictly
  serial. User direction: "一定保留 sq cq" ("MUST preserve SQ/CQ").

  v3 design (single task, inline FU, persistent read future, select race):
    crates/stream/src/extent_node.rs::handle_connection
      • `read_fut: Option<LocalBoxFuture<'static, ReadBurst>>` — owns
        OwnedReadHalf + 512 KiB buf across iterations; NEVER dropped
        mid-flight (io_uring SQE stability). Rebuilt only after the
        future resolves, using the reader + buf returned in ReadBurst.
      • `inflight: FuturesUnordered<Pin<Box<dyn Future<Vec<Bytes>>>>>`
        cap `AUTUMN_EXTENT_INFLIGHT_CAP` (default 64).
      • Loop (per iteration):
          1. drain any ready completions via
             `.next().now_or_never()` → tx_bufs
          2. flush tx_bufs with ONE `write_vectored_all` syscall
          3. branch on (n_inflight, at_cap):
               n_inflight == 0 → await read alone
               at_cap          → await completion alone (back-pressure:
                                 never exceed `cap` in flight)
               n_inflight == 1 → await completion (fast path: in
                                 sustained single-extent pipelining the
                                 client can't submit more until responses
                                 flush, so racing the read has no upside
                                 and costs ~5-10 µs/cycle polling)
               n_inflight > 1  → select(read, inflight.next())
                                 Left wins  → process frames, rebuild
                                              read_fut
                                 Right wins → put read_fut back, extend
                                              tx_bufs

    crates/stream/src/extent_node.rs — new helpers:
      enum ReadBurst { Data{buf,n,reader}, Eof{..}, Err{e,..} }
      fn spawn_read(reader, buf) -> LocalBoxFuture<ReadBurst>

  Correctness proof (NEW integration test):
    tests/extent_pipeline.rs::cq_flushes_fast_ops_while_slow_op_runs
    Sends 1 slow APPEND (64 MB, must_sync=true) + 100 fast READs to
    100 DIFFERENT extents on one TCP connection, all concurrently.
    Measures time to FIRST read response vs time to APPEND done.
    Asserts first_read_elapsed < 0.5 × append_elapsed.

    Measured (5 runs): ratio ~0.37-0.47 (passes, stable margin).
    In burst mode (v2) this ratio would be ~1.0 (first read waits for
    append) — the test precisely distinguishes burst vs true SQ/CQ.
