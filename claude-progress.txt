  根因分析:
    - 之前 MuxPool 按 addr 索引, 同一 ExtentNode 所有 stream 共享 1 条 MuxConn
    - MuxConn.writer 是 futures::Mutex, 跨 await 锁定
    - flush 时 row_stream append 256MB SSTable:
      write_vectored_all 在 loopback TCP 握锁 150-200ms/replica × 3 replicas
    - 期间 log_stream 的 4KB/16KB WAL 批都 writer.lock().await 等待
    - 结果: 每 1.5s (FLUSH_MEM_BYTES=256MB / 167MB/s) 一次吞吐凹槽
    - 小值 (128B) 测试甚至出现 整段 2+s 0 ops/s 完全停摆

  测试:
    - cargo build --release --workspace: 0 error
    - 清洗 /dev/shm/autumn-rs, 起 3× tmpfs cluster
    - perf-check 4KB × 256 threads × 10s: 42881 ops/s (baseline 32491, +32%)
    - perf-check 128B × 256 threads × 15s: 130560 ops/s, p99=3.91ms
      (之前 128B 在 flush 期间完全停摆, 现在仅短暂 20k 凹点后立即恢复)
    - perf-check 4KB × 20s: 40827 ops/s (持续 20s 稳定 35-48k)
    - Read ops/s: 88569 (未变, 读路径不走 mux 写锁)

  关键观察:
    - log_stream lock_wait_ms: before ~150ms during flush → after 0.0 (隔离成功)
    - row_stream (Bulk pool) append_ms 依然 150-900ms (此路径本就是 bulk)
    - inflight_peak = 4 稳定 (F087-followup ring-buffer 持续工作)
    - p99 依然偏高 (37-81ms): 连接层 HoL 已消除, 但 ExtentNode 单机串行写盘仍是下一个瓶颈
    - 回退: 未登记的 stream 默认 Hot → 与之前行为等价, 无需 env 开关

  结论:
    - 连接层 HoL blocking 已解决, log_stream 的"瞬时拥塞"问题消失
    - 小值 (<VALUE_THROTTLE=4KB) 写入路径改善最大 (完全停摆 → 最低 20k ops/s)
    - 4KB/大值路径进一步改善受限于 ExtentNode (参考 memory: ps_write_bottleneck)
    - 下一步性能工作应聚焦 ExtentNode 写盘侧并发/io_uring SQE 批量
